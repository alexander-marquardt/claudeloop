label: "Concurrency & Thread Safety"
---

Review for concurrency issues. Look for: race conditions, shared mutable state without synchronisation, deadlock potential, missing locks around critical sections, non-atomic read-modify-write sequences, and unsafe use of globals. Check async code for missing awaits, unawaited coroutines, and blocking calls in async contexts. Fix any issues you find.

Two async-runtime patterns deserve explicit, high-priority attention because they degrade the whole service rather than corrupting one value:

- **Synchronous blocking I/O on the async request path.** A single blocking call inside an `async def` handler (FastAPI/Starlette/aiohttp) or Node async path stalls the *entire event loop* — every concurrent request on that worker waits behind it — collapsing the throughput advantage of async back toward serial. Flag synchronous network/disk/sleep calls reached from an async handler: `requests.*`, a synchronous Elasticsearch/DB client, `time.sleep`, `open()/read()` of large files, `subprocess.run`, any CPU-heavy loop. The FastAPI-specific footgun is a route declared `async def` that then calls sync I/O directly (a plain `def` route would at least run in the threadpool; an `async def` one does not). Fix: `await` a genuinely-async client, or offload the sync call with `asyncio.to_thread(...)` / `run_in_executor` / the framework's threadpool. When you fix one, ship an isolating test (see below) proving the call now runs off the loop (assert the loop is not blocked, or that the work ran in a worker thread).

- **Missing client-disconnect cancellation on slow handlers.** A long-running request (a heavy query, a fan-out, a large export) that keeps working after the client has disconnected wastes the server's — and any downstream cluster's — capacity on a result no one will read; under load this compounds into wasted throughput that is invisible in tests, which never disconnect. Where a handler does substantial work and the framework exposes disconnect/cancellation (ASGI `request.is_disconnected()`, an incoming cancellation token, `AbortSignal`, context cancellation in Go), long handlers should observe it and stop early. Flag slow handlers that ignore disconnection; fix by wrapping the work so a disconnect cancels it (and returns the framework's client-closed status, e.g. 499). Genuinely fast, idempotent handlers don't need this — don't add cancellation plumbing to a trivial endpoint.

When you fix a concurrency issue, ship an **isolating** test that pins the concurrency-specific behavior the fix introduced — that the blocking call now runs off the event loop (e.g. assert the loop is not blocked, or that the work ran in a worker thread), that the coroutine is actually awaited, that the critical section stays correct under contention (spawn concurrent workers and assert the invariant holds). A pre-existing parity or value-equality test does NOT discharge this: those pass with or without the fix, so they prove nothing about the concurrency behavior — the isolating test should fail against the pre-fix code. If an isolating test genuinely cannot be written in this stack, do not skip silently — add the explicit `no test added: <named missing piece>` line naming the specific harness or fixture that does not exist.
